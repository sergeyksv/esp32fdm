# ESP32 FDM Printer Bridge

WiFi-to-printer bridge firmware for **Freenove ESP32-S3-WROOM** (OV2640/OV3660 camera, dual USB-C).
Dual backend: Marlin (USB serial) or Klipper (Moonraker HTTP).

## Features

- **MJPEG video stream** from OV2640/OV3660 (`/stream`, `/capture`)
- **USB Host** serial bridge to FDM printer (CDC-ACM + CH34x/CP210x/FT23x VCP)
- **Marlin backend**: direct serial, host printing from SD, GCode terminal
- **Klipper backend**: Moonraker HTTP API, file upload + print, temp/progress tracking
- **Bed leveling**: probe mesh (Marlin G29, Klipper BED_MESH_CALIBRATE), color-coded grid visualization, mesh history, screw adjustment calculator with 1/8-turn precision
- **Obico integration**: AI failure detection, remote monitoring; a pause by Obico's failure detection is sent to the hub (Telegram)
- **RFC 2217 server** — OctoPrint connects via `rfc2217://<ip>:2217` (Marlin only)
- **Wait for user**: `M0`/`M1` or a `; @pause <text>` comment in a file printed from SD stops the print without parking, `/print` is the phone page to adjust Z and continue, and the hub sends a Telegram notification. With Klipper the board rewrites the stops in the file it uploads
- **Filament change** (Utils): the new filament pushes the old one out at the hotter of the two plastics' temperatures, with a stop before the purge; the board remembers the loaded plastic
- **Maintenance** (Utils): jobs due by print hours, days or completed prints (the template's "Bed: wash off the glue" every 10), a log, hub reminders; a print started with a job overdue is logged and reported, and the board's print buttons ask first
- **Nozzle guard** (Settings): a wait keeps ABS from charring in a hot nozzle: before the first layer it purges, then goes to a standby temperature; during a print or a pause because the filament ran out, standby after a while, and at once for a pause from Obico; Continue heats back first
- **Checks before a print**: a Z offset that a bed calibration changed (Marlin; the Kobra measures it wrong on its pad) and a Klipper mesh profile that no longer matches the bed's last probe are shown on `/print` and the bed page, asked about by the board's Print buttons, and reported to the hub when a print starts anyway
- **Cold pull** (Utils): pick a plastic and the board runs a built-in nozzle-cleaning script as a host print, stopping with a notification each time the user has to pull or reload the filament

## Build

Requires ESP-IDF v5.4 installed at `~/esp/esp-idf`.

```bash
source ~/esp/esp-idf/export.sh
idf.py set-target esp32s3
idf.py menuconfig   # Set WiFi SSID/password under "ESP32 FDM Bridge Configuration"
idf.py build
idf.py -p /dev/ttyUSB0 flash monitor
```

## Hardware

- **Right USB-C:** UART bridge — flashing/debug
- **Left USB-C:** ESP32-S3 native USB (GPIO19/20) — OTG Host to printer
- **Camera:** OV2640 or OV3660 on DVP (GPIOs 4-18, no conflict with USB)
- **PSRAM:** 8MB OPI (Octal, 80 MHz) — camera frame buffers, TLS, many task stacks, and the code itself (`SPIRAM_XIP_FROM_PSRAM`)
- **Flash:** 16MB — 4MB app (dual OTA), ~12MB LittleFS cache partition

## Core Affinity

- **Core 0:** WiFi, HTTP server, RFC 2217 server + TX drain
- **Core 1:** USB Host lib, device poll, CDC-ACM driver (priority 20)

## Architecture Notes

- `usb_serial.cpp` must be C++ because VCP driver headers are `.hpp`
- C++ exceptions enabled (`CONFIG_COMPILER_CXX_EXCEPTIONS=y`) — required by VCP component
- Camera XCLK at 20 MHz, SVGA JPEG Q12, 2 DMA buffers with GRAB_LATEST
- RFC 2217 uses FreeRTOS StreamBuffer to decouple USB RX callback from TCP send
- Single RFC 2217 client at a time (matches OctoPrint usage pattern)
- OTG port may not supply 5V VBUS — user may need powered USB hub
- `printer_backend_t` enum lives in `printer_backend.h` to break circular include between `layout.h` and `printer_comm.h`
- Klipper SD print: uploads from local SD to Moonraker with size-based dedup, auto-deletes previous upload
- Marlin host print uses line numbering + checksums; M110 N0 reset on finish to prevent resend loops
- Terminal and RFC 2217 hidden from UI when Klipper backend is selected
- GCode file info (layers, time, filament, thumbnail) cached in `/cache/gcode/` on LittleFS — keyed by filename + file size, LRU eviction at 50 entries
- Bed mesh auto-captured from any G29 output (probe button, terminal, printer UI); history stored in `/cache/beds/`, LRU eviction at 100 entries
- Screw adjustment: 4-screw centered layout, configurable bed size/origin/pitch, tighten or loosen mode, 1/4 + 1/8 turn display
- `M0`/`M1` in a host print are never sent to the printer, and `; @pause` is the form for start files shared with other printers. A hold is `paused` plus `holding`: no parking, no M76 (the printer's UI must stay in print mode), and no `M84 S<n>`: on the Kobra 2 build it makes Marlin drop every babystep, from `M290` and from the printer's own Z buttons, until the next `G28`. It cancels the print after `CONFIG_HOLD_TIMEOUT_MIN`
- Hold beeps are played one `M300` at a time from `hp_tick()`, 0.6 s apart: the Neptune 3 Pro drops an `M300` that arrives while one is playing (and ignores `S0` rests), and a blocking loop would delay Continue and Z taps
- Continue from `/print` carries the hold id, so a double tap cannot skip the next M0
- Z taps on `/print` skip the command queue and accumulate in `host_print.c`, then go out as one `M290` when the printer is ready. A step sent without a reply counts as applied and is never resent, since it may have moved the nozzle
- A host print starts at once: the whole-file scan runs in its own low-priority task with its own file handle, and `preparing` is set until it finishes. Progress and layer counts are unknown until then
- A built-in script (cold pull) is a host print from a malloc'd buffer read through `fmemopen`, so no SD card is needed and every print feature applies. The buffer waits in `host_print.c` while `PCMD_HOST_SCRIPT` carries only the name, belongs to the print from then on, and is scanned in place rather than in the scan task, which could outlive it
- A built-in script can pass a `host_script_done_t` that the printer task calls when it ends (completed or cancelled). Filament change and cold pull use it to record the plastic in the nozzle: the new one when the script completes, the hotter of the old and new when cancelled, since either may be there
- With Klipper a built-in script is uploaded as `<name>.gcode` from memory (`fmemopen`, always sent: its numbers change without changing its size) and printed, from its own task since the Neptune 4 answers the start only after the script's G28. The end is seen in the poll: completed only on print_stats `complete` (Elegoo's CANCEL_PRINT resets the file, so a cancel shows as `standby`), and the done callback runs on the poll task. A reboot during the script loses the callback and, since the script is not on the SD card, its stops
- The Marlin send/wait logic (`marlin_send_cmd_ex()`, `process_line()`, the host print's sender) has been changed many times; run `test/host/run.sh` before and after touching it. The tests compile `printer_comm.c` and `host_print.c` unchanged on the PC with stand-in headers (`test/host/stubs/`) against a simulated printer on a simulation clock (`sim.c`: commands run in order with Marlin's answers; switches for answers held until the next OUT, all of them or only some commands', busy keepalive, a dead printer), and run the real printer task loop for scripts. `TEST` cases pin what works; `KNOWN` cases state the behaviour wanted for problems seen on real printers (fdm05's G28 answer held until the next command; a timed-out command's late `ok`, or a ping's own `ok`, taken as the next command's) and are reported, not failed, until they pass, then the run fails until they become `TEST`s. A `busy: processing` while the board waits for its command's `ok` (the host print turns on the `M113 S2` keepalive; a long move with the planner full sends it) keeps the wait going, and that `ok` ends the 4 s busy cooldown: before, the board sent nothing for 4 s and the planner ran dry (fdm20, 20.11.26: the brim stopped in the same corner every loop)
- Nozzle guard (`nozzle_guard.h`, Settings, section `nozzle` of the copied settings): ABS left hot in a waiting nozzle chars and ruins it. In a wait for the user (M0/M1/`; @pause`, both backends) before the first layer (no `;LAYER:`/`;LAYER_CHANGE` yet in a file that has them: Marlin from the host print's markers and the scan's layer count, Klipper from `klipper_hold_t.before_layers`, set by `klipper_holds.h`) it pushes `purge_mm` out every `purge_every_s` for `purge_for_min` (5 mm / 2 min / 15 min), then retracts 2 mm and sets the standby temperature; later in the file (the nozzle is over the part) no purge, standby after `mid_after_min` (10). A pause from Obico (`printer_cmd_t.standby`) goes to standby at once. A pause because the filament ran out is a wait in the print (standby after `mid_after_min`, so someone who comes at once finds the nozzle hot) and sends the hub `filament_runout` at once: Marlin, the board's own pause in a host print (`printer_cmd_t.runout`, from `M119` "filament: open" or `//action:out_of_filament`), parked and retracted already, so no retract; Klipper, a pause (the printer's `pause_on_runout`) while the first `filament_switch_sensor`/`filament_motion_sensor` in the objects list is enabled and shows no filament (added to the poll's query), standby with `M104` and Continue as after a pause from Obico (`s_pause_restore_c`). A runout the printer handles itself in `M600` (a Marlin SD print, or the printer's own sensor first) is not covered: Marlin runs no command from the host until the user confirms. Continue heats back first and waits (Marlin `M109` from the printer task, Klipper `M109` in the Continue script, whose answer may come after the 10 s request timeout and then counts as sent, since a second Continue would push the filament back twice; no beeps once Continue is sent, they would play in the print), then pushes back the retract. Standby by plastic (0 = off; PLA off, PETG and ABS 160, Nylon 170); a plastic without one printed at 230 °C or more gets ABS's, since the plastic on record may be old. The guard's own E moves put the file's extruder back: Marlin follows M82/M83/G90/G91/G92 and the last E through the lines sent (`track_e`) and ends with `M82` + `G92 E<last>` or `M83` (the unpark after a parked pause also restores the file's E mode now, it forced `M83`); Klipper wraps them in `SAVE_GCODE_STATE`/`RESTORE_GCODE_STATE`. A pause from Obico on Klipper: `M104` after `/printer/print/pause` (Elegoo's PAUSE has saved the temperature, and its RESUME heats back by itself if resumed on the screen); the board's resume sends `M109 S<t>` + `RESUME` as one script. Other pauses made on the printer are left alone (resumed from its screen, they would print cold); a Marlin SD print (not a host print) gets no standby either. `/api/status` `nozzle` is `hot`, `standby` or `heating`, shown on `/print`; the hub gets `nozzle_standby`. The hold timeout is 120 min (it was 30), as a nozzle at standby can wait
- Checks before a print (`print_checks.c`). The Kobra 2 Neo measures the Z offset on its pad at every bed calibration and misses by tenths of a mm either way, while the real offset (nozzle to probe) stays; a print after a calibration scratched beds. The board reads `M290` ("Probe Offset Z-0.97") on connect, every minute while idle and right after it captures a mesh, and keeps a checked offset (NVS `checks/good_z`): the first one seen, the one at the end of a completed print, the paper test's, one set with Z taps in a print that the printer still has when idle, or Keep. An idle reading that differs by 0.015 or more is the warning, with Put back (`M851 Z<checked>` + `M500`; the Kobra answers `M851` as `M851 X24.00 Y13.35 Z-0.97`), Keep, or Check with paper. Klipper: the profile the printer prints with (`print_mesh_name()`: chosen, else the one loaded at start) is compared with the last probe in the history, at the probe's points within the profile's area, as max minus min of the difference (a shift is the Z offset's business); 0.2 mm or more is the warning (fdm19, 19.11.26: a 6x6 probe after turning screws was 1.75 mm off profile 11, which scratched the bed). The check reads Klipper's mesh first, so a probe from the screen counts, and is cached for 30 s. `GET /print/checks` carries the overdue maintenance too (`n`, `text`) for the Print buttons' question, plus `warn` and, for the Z offset, `z`; a print that starts with a warning (any start, from the print_stats task) sends the hub `print_check`, in the language of the last page that asked
- Marlin runs M104/M106 as soon as they are read, not after the moves queued before them: a script that must heat or cool after a move (the cold pull purge) needs M400 in between
- `/print` is the operational screen, inside the common layout (the layout's status line is hidden there, the page shows the same state itself); home stays the manual control page. It polls `/api/status` every 1.5 s (`fan` and `plastic` were added for it: Klipper `fan.speed`, Marlin from M106/M107 in a host print), `/maintenance/due` every 60 s, and reloads `/capture` every 5 s
- Raise Z (`/print/lift`) never homes: a print may be on the bed, and the Kobra probes in the middle. Marlin moves `G91`/`G1 Z100`/`G90` from the position it kept after M84 (soft endstops clamp). Klipper refuses moves unhomed, so `klipper_backend_lift_script()` uses the last toolhead Z seen with `z` in `homed_axes` (cleared when a poll fails, since a Klipper restart zeroes the position): `SET_KINEMATIC_POSITION Z=<it>` (Elegoo has `[force_move]`), the move, then `M84`, because that command marks every axis homed. The move is clamped to `axis_maximum` − 2 mm and sent from its own task, since Moonraker answers when the move is done. `motors` in `/api/status` is Klipper's `homed_axes` non-empty, −1 on Marlin (no way to ask), and the Motors off tile hides only on 0
- Set Z offset (`/print/zoffset`) is a built-in script: G28, the nozzle to Z0 at the bed centre (`bedlevel_bed_center()`), a `; @pause`, then Z10. Marlin ends with `M500`, since M290 moves the probe offset; on Klipper the script starts with `; @zoffset` (from the board's saved offset) and its done callback saves `probe_z_offset` (the gcode offset) with `klipper_backend_set_zoffset()` when it completes. The Z taps are the hold's, with the 3 mm limit of a built-in script (`z_shift_limit_cu()`; 1 mm in a print), since after screw turns the bed often moves more than 1 mm
- "Print again" on /print starts only a file from the recent list (NVS, newest first), since the page is opened from the hub and Telegram
- Each board with a hub URL also reports its status every 10 s and on every state change (`/api/v1/status`), for the tile dashboard the hub serves at `/`
- The web UI is translated gettext style: the English text in the code is the key, and `i18n/<lang>.po` holds the translations, turned into `i18n_tables.c` at build time. `HTTPD_REGISTER` wraps every handler so the language (cookie `lang`, else `Accept-Language`) is set per request in a thread-local. Big page templates mark text with `N_()` and go through `i18n_page()`, which builds each template once per language in PSRAM. The generator fails the build on a translation whose `%` formats differ or that adds `"`, `<`, `>`, `&` or `\`, and turns `'` into `’` so a translation cannot close a JavaScript string. After changing marked text run `python3 tools/i18n.py update` and translate the new entries
- The language lives in a thread-local, so text built in another task (an async handler, a probe task) is English unless the handler passes `i18n_lang()` along and the task calls `i18n_set_lang()` (see `logbuf.c`, `ota.c`), or the text is built later in the request that shows it (see `bedlevel.c`)
- On a phone (under 560 px) the nav is the brand, the page name and a menu button that opens the links as a list; on wider screens the brand is the Home link. CPU bars and the language switch are in the footer
- Boards send events, not Telegram messages: the bot token and chat exist only on the hub
- Obico sends `{"commands":[{"cmd":"pause","args":{...},"initiator":...}]}`: its failure detection pauses with initiator `system` (obico-server `pause_if_needed`), a user in the Obico app with `api`. Only `system` sends the hub `obico_pause`
- An OTA upload while the printer is busy (printing, paused, error, a user command such as G29 running, OctoPrint connected) is not written to flash: erasing 1.5 MB stalled the caches, and both cores with them, for half a minute and would starve a host print (measured before the code moved to PSRAM; with `SPIRAM_XIP_FROM_PSRAM` ESP-IDF keeps the cache on during the erase, not measured again). The image waits in PSRAM, checked at upload time by its appended SHA-256, and `ota_defer` installs it after `DEFER_IDLE_S` (60 s) with no heater target and no user command. If a print starts during the write, the reboot waits for it. After that reboot `ota_report_update()` sends the hub an `updated` event (`update_failed` if the write fails). So a flash command no longer has to check the state first, but boards on 2.4 or older still flash at once. A Klipper board does not defer for a print (Klipper prints on its own host): only while it sends a file to Moonraker or a built-in script runs, and then without the 60 s idle wait
- Print statistics are the board's own count (the Kobra's Marlin has no `M78`): a task samples the state every 5 s and counts PRINTING without a hold. A host print reports how it ended (`last_host_completed`); for a printer SD print, which the board only sees stop, 99 % progress counts as completed. Built-in scripts (`builtin_script`) are not counted. Saved every 10 min while printing and at each start and end, so a power cut loses up to 10 min. The module is `print_stats`, not `stats`: lwIP defines a `stats_init()` macro. With Klipper, print_stats `complete` sets `last_host_completed`, and the first time a board sees Moonraker's `/server/history/totals` it takes those hours and jobs if they are more than its own (NVS `stats/mr_seeded`), shifting maintenance by the same amount
- Maintenance jobs and their log live on LittleFS in `/cache/maint` (`jobs.json`, written aside and renamed; `log.txt`, one JSON line per entry, trimmed from 300 to 200), not NVS: with descriptions the list is a few KB and NVS is 24 KB shared with Wi-Fi. The cache housekeeping only evicts in its own folders. Template jobs keep the English msgid for name and description, so the page shows them translated; text saved that equals a template text in any language is stored as its msgid. User text is escaped on output (`put_esc`), not stripped. Reminders go out from a 60 s task when the printer is not printing, once per job until Done, in the language of whoever last saved the list. Setting the print hours by hand shifts every job's "done at" by the same amount. A job can also be due by completed prints (`print_stats.completed`; "done at" keeps that count too): the glue job of the template counts 10, and a list saved before it (`"v"` below 2 in jobs.json) gets it added once. When a print starts (the print_stats task, so any start, also from the printer's screen) with a job overdue, `maintenance_note_print_start()` writes a log line with `"w": true` (the overdue text and the file) and sends the hub `maintenance_skipped`; the stats task stack (8 KB, PSRAM) takes that LittleFS write. The board's own Print buttons ask first through `GET /maintenance/due`
- Copying settings: each module exports and imports its own section (`*_settings_export/import`), and `settings_copy.c` lists the sections. The browser does the copying: the settings page fetches the other board's `GET /api/settings` (CORS `*`), shows the sections, and posts the chosen ones to its own board; the board list comes from the hub's `/api/v1/printers`, also CORS `*`. A new setting that is the same on every printer of a model belongs in a section; anything that identifies the board (name, Obico token, Moonraker address) or is its history must stay out
- Wi-Fi: after boot the `wifi_mgr` task owns the connection and retries forever (5 to 60 s apart), scanning and choosing the AP each time: the preferred one if -75 dBm or better, else the strongest. Before, three failed retries after a lost connection left the board offline until a reboot. 802.11k/v is on (`CONFIG_ESP_WIFI_11KV_SUPPORT`): a disconnect with `WIFI_REASON_ROAMING` (207) is the network moving the board (DAWN), and the supplicant reconnects by itself, so the handler must not; the task steps in only if it is not back after 20 s. The task's own AP switches set `s_switching` so their disconnect is not taken as a loss
- Klipper has no M0/M1, so `klipper_backend_print_file()` reads the SD file twice: once to find the stops and the size as sent, then to upload it with each stop rewritten into `M117 <text>`, `M400`, `M25`. `M25`/`M24` are virtual_sdcard's own pause and resume: Klipper's `PAUSE`/`RESUME` would run the printer's macros (the Neptune 4's park, retract 22 mm, and purge 100 mm on resume), and `BASE_PAUSE`/`BASE_RESUME` restore the gcode state, which would undo a Z offset set while waiting. A pause is one of our stops when virtual_sdcard's `file_position` equals the end of a rewritten stop and `file_size` is the size we sent. After a reboot the board scans the running file on the SD card again to get its stops back. Z goes out as `SET_GCODE_OFFSET Z_ADJUST=<d> MOVE=1`, beeps as one script of three `M300` if the printer has an M300 macro. Moonraker's size check for an unchanged file compares the size as sent
- Z offset on Klipper: Elegoo's screen keeps its offset in its own file (not under Moonraker's roots, not in printer.cfg) and sets it with `SET_GCODE_OFFSET Z=` at power-on (twice: right after Klipper is ready, and again about 75 s later), so the board cannot save into it. The board keeps its own (NVS `klipper/z_offset`, thousandths of a mm, saved from the dashboard as Klipper's current gcode offset) and `klipper_holds.h` turns a `; @zoffset` line into `SET_GCODE_OFFSET Z=<it> MOVE=0` in every file it sends; without a saved offset the line stays a comment. The Klipper poll reads `gcode_move.homing_origin` into `probe_z_offset`, which the dashboard shows, and takes Z from `gcode_move.gcode_position` (G-code coordinates, offset excluded). The dashboard's Z- never goes below 0 (the Neptune 4 Max allows -5): it keeps its own Z estimate from the taps since the last status, and Z0 lowers to 0 in one move, for setting the offset with paper
- The Klipper poll's query is near 300 characters: `http_get`/`http_post` build the URL in 512 bytes and refuse one that does not fit, since Moonraker answers a cut query without the objects it lost
- Bed leveling on Klipper: the status request reads `bed_mesh.probed_matrix` with `mesh_min`/`mesh_max` and keeps it in `/cache/beds` when it differs from the last one, so a mesh probed elsewhere shows too. Probing is a built-in script ("Bed mesh"), whose done callback marks the mesh to be read. Meshes with coordinates get the screw plan, computed in the page: bilinear height at each screw (straight on past the edge points), target = the line through two fixed supports, the plane through three or more, or the middle screw height; rounded to the chosen step (`turn_div`: 1/8, 1/6, 1/4 or 1/3 turn) of the pitch. If the tilt no screw can take out (along two fixed supports, or of the plane through three or more) is over 2 mm over the screws' span (1 mm until 19.11.26: fdm19 with its screws turned at random showed 1.3 mm, more likely the plate bent by one low corner than the carriage), the page shows no screw plan, only "fix the mechanics first": with the Neptune 4 Max's fixed middle supports a carriage riding tilted (worn wheels) gives several mm that way, and screw advice against it is nonsense. Meshes without coordinates (Marlin) keep the quadrant calculation. A mesh equal to the saved points of its active profile (other than "default") is a profile loaded at start, not a new probe, and is not added to the history (the Neptune 4's screen loads profile 6 or 11 at power-on, maybe from before the screws were turned). "Save mesh for printing" probes with `PROBE_COUNT=n,n` when the profile name is a number, `BED_MESH_PROFILE SAVE=<name>`, and once the script is over and the mesh read, `SAVE_CONFIG`. The profile defaults to the one the printer loads at start: the Klipper backend watches `bed_mesh.profile_name` for 3 minutes after Klipper comes back and keeps the first one other than "default" (NVS `klipper/boot_mesh`)
- Memory (measured with `/api/heap` and `/api/tasks` on fdm06, a Marlin board with Obico, 2026-11-16). Internal RAM went from 28 KB free with a largest block of 7 KB, below the 8 KB the OTA task stack needs, to ~97 KB free with a largest block of 31 KB (the ceiling of one memory region). What did it: TLS allocates in PSRAM (`CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC`; each connection took 25–30 KB with its 16 KB input buffer); most task stacks are in PSRAM (`task_create_psram()` in `task_util.h`). Every ESP_LOG line takes over 1 KB of the calling task's stack (the `/logs` hook formats into a 512-byte buffer, then vsnprintf and the UART): the `led` task had 2560 bytes and overflowed when it switched the light at a print's start or end (PANIC on fdm05 and fdm23 until 2.6), so give a task that logs at least 4 KB. Stacks (2.6, 2026-11-17): a task's stack goes in PSRAM, where it can be generous (8 KB, 12 KB with HTTP, TLS or the printer protocol) instead of cut to its measured use, unless it is a driver (USB, camera DMA), an SD upload or print start loop (sd_upload, sd_wr, sd_print, print_again, sd_format), OTA, or ESP-IDF's own (httpd 10 KB, Wi-Fi, lwIP, timers); those are internal with a margin (6–8 KB). Flash is fine from a PSRAM stack: with `SPIRAM_FETCH_INSTRUCTIONS` + `SPIRAM_RODATA` ESP-IDF keeps the cache on during flash reads and writes (`SPI_FLASH_CACHE_NO_DISABLE` in `spi_flash_os_func_app.c`; an hour of NVS and LittleFS writes from two such tasks on fdm13 gave no error), and a 7 MB G-code scan takes the same time with its stack in PSRAM as in internal RAM, also with the camera streaming. Still forbidden on a PSRAM stack: mapping flash (`spi_flash_mmap`, `esp_partition_mmap`) and the OTA functions on it (`esp_ota_end`, `esp_ota_set_boot_partition`, `esp_ota_mark_app_valid_*`, the first `esp_ota_get_running_partition`), which disable the cache and assert; and a stack buffer handed to DMA (SDMMC bounces it a sector at a time). A task made with `task_create_psram()` ends with `task_delete(NULL)`, which picks `vTaskDeleteWithCaps()` for it (`vTaskDelete()` would leak its stack, and `vTaskDeleteWithCaps()` asserts on an ordinary task, which the helper makes when PSRAM cannot take the stack). Overflows: the canary stays, `FREERTOS_WATCHPOINT_END_OF_STACK` stops on a write to the last 32 bytes of the running task's stack, and heap_mon checks every task's high water mark each minute: under 768 bytes it logs and sends the hub `stack_low` once per task per boot (ESP-IDF's IDLE and ipc tasks, ~520 bytes by design, are skipped). rfc2217 runs on Marlin boards only. Code and constants run from PSRAM (`SPIRAM_XIP_FROM_PSRAM`, ~1.5 MB of the 8 MB; idle CPU load about halved, OTA write 15 → 10.5 s); the CPU runs at 240 MHz. The flash stays in DIO: OTA never rewrites the DIO bootloader, and with the code in PSRAM QIO would gain little
- Light during a print (Settings, `board_led.c`, section `light` of the copied settings): the board's RGB LED in white (the default), the printer's own light, both or none; on when PRINTING or PAUSED starts, and the end switches off what the start switched on. The printer's light is a command: by default `M355 S1 P255` / `M355 S0` on Marlin (the Neptune 3 Pro's light bar; its M115 lists `TOGGLE_LIGHTS`), `FDM_LIGHT S=1` / `S=0` on Klipper, sent only if `/printer/objects/list` has that macro (rechecked after a failed poll and every minute, since a quick `RESTART` can fall between two polls). The Neptune 4 Max's top light (the one wanted during a print) is host GPIO `gpio66`, which Elegoo's screen app (`znp_tjc_klipper`, root) holds at the state of its own button, so only the app can switch it, through a file it watches; it answers `3` / `2`. Which file depends on the app: the 2024 build (fdm14, fdm15; Klipper v0.10.0-530 with `gcode_shell_command`) takes `/home/mks/gpio66_value` (`tools/klipper/neptune4-esp32fdm.cfg`); there `gpio79` (`MODLELIGHT_SWITCH`) is a ramp light with extra fans not fitted here, never switch it. The 09.2025 build (fdm16, fdm19: the newer toolhead, its own MCU `THR` on a USB-C cable; Klipper without `gcode_shell_command`, so its own `FLASHLIGHT_SWITCH` is broken; `[output_pin caselight1]` on `THR:PB10` is the light in that toolhead, not wanted during a print; SSH user `neptune4`) drives `gpio66` and `gpio79` together from one variable, set only from `/home/mks/gpio79_value`; `gpio66_value` is answered but ignored (found in its machine code, 2026-11-19). That image needs KIAUH's `gcode_shell_command.py` in `~/klipper/klippy/extras/` and `tools/klipper/neptune4-2025-esp32fdm.cfg`. Either way: the file goes to the config root as `esp32fdm.cfg`, `[include esp32fdm.cfg]` into printer.cfg, restart Klipper. Other printers: type their commands in the two fields
- Formatting the SD card (`/sd`, `POST /sd/format`): refused while printing or paused, while a host print runs, during an upload or a send to Klipper; it runs in its own task and the page polls `card` in `/sd/status`. A mounted card goes through `esp_vfs_fat_sdcard_format()`, one that did not mount is mounted again with `format_if_mount_failed`; FAT32 with the mount's 16 KB clusters, also over 32 GB (exFAT is off, and only the board reads the card). A file left open across it only fails its next access (FatFs checks the mount id). The recent list needs no clearing: `/print/recent` offers only files on the card
- Reading a whole file from the SD card (Klipper upload, the whole-file scan at a host print start, G-code info middle): `read()` on the descriptor into internal DMA memory (16 KB, halved until it fits), not `fread()`. stdio reads through FATFS's per-file sector cache, which is in PSRAM here (`FATFS_ALLOC_PREFER_EXTRAM`) and reached by DMA only through a bounce buffer: 1.4 MB/s against 4.5 MB/s, and the 1-bit SDMMC bus at 40 MHz tops out at 5 MB/s. The whole-file scan at a host print start went from 19.1 s to 4.3 s for a 7.2 MB file (fdm13); it counts lines as the sender's `fgets(256)` does, so progress stays exact, and a built-in script (fmemopen, no descriptor) still goes through `fgets()`. The Klipper stop rewriting rejects a line by its first characters (`kh_maybe_stop`) and keeps its state in internal RAM; read plus rewriting goes at 3.5 MB/s
- `FW_VERSION` (`main/version.h`) is the release and the app descriptor's version; `FW_BUILD` ("16.11.26 14:32 deee079+") is generated on every build by `tools/build_stamp.py` (rewritten only when it changes, so a build in the same minute relinks nothing) and shown in the footer, `/api/status`, the hub status and tiles. The image carries it after a `FWBUILD=` tag, which `ota.c` finds in a deferred image (the needle is built at run time, or it would find itself) for the pending version and the `updated` event
- The nav brand is the board's hostname on `/print`, `ESP32FDM` elsewhere
- Sockets: `LWIP_MAX_SOCKETS` is 32. The web server takes up to 15 (13 connections plus its listening and control sockets), and it closes the oldest idle connection only at its own limit of 13. With 16 (until 2.6) browsers holding keep-alive connections to `/print` used up every socket on fdm14 (a Klipper board with Obico): the server accepted and dropped every new connection, the Klipper poll showed the printer disconnected, and the hold event to the hub failed. Keep the total well above 15 plus the clients (Klipper poll, hub, Obico WS and uploads, Janus, RFC 2217)
- The `/logs` ring lives in PSRAM `.noinit` (`CONFIG_SPIRAM_ALLOW_NOINIT_SEG_EXTERNAL_MEMORY`), so a panic, watchdog or `esp_restart` keeps it and each boot adds a `==== reboot #N: reason=... ====` line. Power loss or brownout wipes it, and so may a new firmware that moves the segment. Each write is flushed from the cache, or the last lines before a crash would be lost. A crash writes its own report there: `logbuf.c` wraps ESP-IDF's `esp_panic_handler` (`-Wl,--wrap` in `main/CMakeLists.txt`) and, before handing over, appends "panic:" lines with the reason (for an abort its text, e.g. "A stack overflow in task led"), the task, the PC, the build and the backtrace (decode with `xtensa-esp32s3-elf-addr2line -pfiaC -e build/esp32fdm.elf` on that build's ELF). Interrupt watchdog resets come through it too; a brownout does not (it is a hardware reset). That code runs in the panic handler: no locks, heap or printf, and one `Cache_WriteBack_All()` at the end instead of the per-write flush
